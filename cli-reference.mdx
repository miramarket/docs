Full reference for every `miramarket-cli` command. For installation and a first walkthrough, see [CLI](/cli). For the strategy JSON format and correctness rules, see [/agent-strategy-guide.md](/agent-strategy-guide.md).

Every command supports `--json` for machine-readable output. In `--json` mode, stdout carries exactly one JSON object and nothing else — no banners, color, or spinner frames — except `login --events` and `strategies watch --events`, which print one JSON object per line (NDJSON), noted below. Piping to a non-TTY also disables color and spinners automatically.

## Envelope and exit codes

Every command that supports `--json` emits the same envelope shape on both success and failure:

```json
{
  "ok": true,
  "command": "account status",
  "...": "command-specific fields"
}
```

On failure, `ok` is `false` and the envelope also carries a human-readable `error` and a machine-readable `code`:

```json
{
  "ok": false,
  "command": "post",
  "error": "Not authenticated. Run `miramarket-cli login` first.",
  "code": "NOT_AUTHENTICATED"
}
```

Prefer branching on `code` over parsing `error` text — `error` wording can change, `code` is the stable contract.

| Exit code | Meaning |
| --- | --- |
| 0 | Success |
| 1 | Generic / unexpected failure |
| 2 | Validation failure |
| 3 | Authentication failure (not signed in, login revoked or ended, or a switch the login doesn't have) |
| 4 | Server failure (upstream error, geo-restricted, timeout) |
| 5 | Bad input (missing file, malformed JSON, missing/invalid flags) |

`code` values include `NOT_AUTHENTICATED`, `LOGIN_DENIED`, `LOGIN_CODE_EXPIRED`, `LOGIN_OUTDATED`, `LOGIN_NOT_ALLOWED`, `FORBIDDEN`, `VALIDATION_ERROR`, `INPUT_ERROR`, `SERVER_ERROR`, `PARSE_ERROR`, `STRATEGY_NOT_FOUND`, `REGION_RESTRICTED`, `WALLET_NOT_DELEGATED`, `WATCH_TIMEOUT`, `INVALID_STRATEGY_STATE`, `NO_ACTIVE_RUN`, `LOCKED_NODE_EDIT`, `UNSUPPORTED_FIELD`, `RUN_EDIT_REJECTED`, `IDEMPOTENCY_KEY_REUSED`, `APPROVAL_NOT_FOUND`, and more — this set grows over time, so don't treat it as closed.

## Sign-in commands

### `miramarket-cli login [--force] [--events] [--json]`

Signs in with the OAuth device authorization grant: prints a short code and a link, you approve it in any browser (doesn't need to be the same device — useful over SSH or on a headless machine), and the CLI finishes automatically once approved. The link opens `https://app.miramarket.org/oauth/device?code=BCDF-GHJK`; the code expires after 10 minutes.

On that page the account owner signs in, checks the code, and chooses what this login may do:

| Switch | Scope | Default | Allows |
| --- | --- | --- | --- |
| **Read your account** | `account:read` | always on | Balances, positions, strategies, runs. |
| **Create strategies** | `strategies:write` | on | Draft, edit, rename, delete, and run simulations. |
| **Trade with real money** | `trade` | on | Start live runs while their combined principal stays within the budget; a start beyond it waits for the owner's approval. |
| **Place orders and bridge** | `orders` | on | `trade`, `order cancel`, and `bridge execute`. Each buy or bridge up to the budget; sells are never capped. |
| **Withdraw funds** | `withdraw` | off | `account withdraw`, to any address, with no limit. |

The budget (default `$100`) is one dollar amount for both live runs and single orders. The login lasts 90 days and appears on **Connected agents** (`https://app.miramarket.org/settings/agents`) as **Miramarket CLI** followed by the computer's name, where the owner can change its budget or revoke it.

| Flag | Description |
| --- | --- |
| `--force` | Start a new login even if a valid one is cached, for example to switch accounts or to change the switches. Revoke the old login on Connected agents, or with `logout` first. |
| `--events` | Agent mode (implies `--json`). Prints one NDJSON `verification` line as soon as the code exists (below), then the final envelope line. With a valid cached login, only the final line (`alreadyAuthenticated: true`). |
| `--json` | Prints nothing until the login is approved, so an agent can't show the human the code with it; agents use `--events`. |

With `--events`, the first line looks like this; show the human `verificationUrl` and `userCode`:

```json
{"event":"verification","verificationUrl":"https://app.miramarket.org/oauth/device?code=BCDF-GHJK","userCode":"BCDF-GHJK","expiresAt":"2026-11-03T10:10:00.000Z","requiredAction":"Show this URL and code to the human and ask them to approve the login in a browser. This command exits once they do."}
```

Without `--force`, a valid cached login short-circuits the command with a notice. The envelope reports `scopes` (what was allowed) and `manageAt` (the Connected agents page). A denied login exits `3` with `LOGIN_DENIED`; a code that expired before approval exits `3` with `LOGIN_CODE_EXPIRED`. A login from a CLI older than 1.6.0 no longer works: commands report `LOGIN_OUTDATED` (exit `3`) and `login` starts a new one.

Signing in does not by itself make the account trade-ready — see `account setup` under [Account commands](#account-commands) below.

### `miramarket-cli logout`

Ends this login: revokes it on the server, so it stops working at once and shows as revoked on Connected agents, and removes the cached login from this machine. The envelope's `revoked` says whether the server could be reached; the local login is removed either way.

### `miramarket-cli auth status [--json]`

Reports whether a valid login is cached, what it may do, and its live-run budget. Always exits `0` — this is a diagnostic, read the payload:

```json
{
  "ok": true,
  "command": "auth status",
  "authenticated": true,
  "postingAllowed": true,
  "did": "did:privy:...",
  "expiresAt": "2026-05-09T12:00:00.000Z",
  "scopes": ["account:read", "strategies:write", "trade", "orders"],
  "liveBudgetUsd": 100,
  "openLiveUsd": 40,
  "connectionExpiresAt": "2027-01-31T12:00:00.000Z",
  "manageAt": "https://app.miramarket.org/settings/agents"
}
```

`postingAllowed` is whether the login may create strategies. `openLiveUsd` is the principal of this login's live runs still in the market. The budget fields are `null` when they can't be read, for example offline. A login from an older CLI reports `authenticated: false` with a `requiredAction` to sign in again.

A command the login wasn't allowed exits `3` with a message naming the switch (`code` is `LOGIN_NOT_ALLOWED` or `FORBIDDEN`); approve a new login with it on (`login --force`).

## Updating the CLI

### `miramarket-cli update [--check] [--json]`

Updates the CLI to the latest release on npm, with the package manager it was installed with and in the same place. No login needed.

| Installed with | What `update` runs |
| --- | --- |
| `npm install -g` | `npm install --global --prefix <this copy's prefix> @miramarket/cli@<latest>` |
| `pnpm add -g` | `pnpm add --global --global-dir <this copy's global dir> @miramarket/cli@<latest>` |
| `yarn global add` | `yarn global add --global-folder <this copy's global folder> @miramarket/cli@<latest>` |
| `bun add -g` | `bun add --global @miramarket/cli@<latest>`, with `BUN_INSTALL` set to where this copy lives |
| `npx`, a project dependency, or a source checkout | Nothing; exits `5` with the command to run instead. |

Each install is pinned to where the running copy lives, so a different `npm` on `PATH` (nvm, Homebrew) can't update another copy. Afterward it reads the installed version back and fails if a different version, or none, landed there. `--check` only reports whether a newer release exists and installs nothing. With `--json`, the installer's own output is captured, so stdout carries exactly one envelope:

```json
{
  "ok": true,
  "command": "update",
  "currentVersion": "1.6.0",
  "latestVersion": "1.7.0",
  "installedWith": "npm-global",
  "updateAvailable": false,
  "updated": true,
  "previousVersion": "1.6.0",
  "version": "1.7.0"
}
```

With `--check`, `updated` is `false`, `updateAvailable` says whether a newer release exists, and `nextCommand` says what to run.

Exit codes: `0` updated, already up to date, or `--check`. `1` the installer failed (`UPDATE_FAILED`), had no permission to write to the install directory (`UPDATE_PERMISSION_DENIED`; re-run with those rights, for example `sudo miramarket-cli update`), or left a different version or none where this copy was (`UPDATE_NOT_APPLIED`). `4` the npm registry is unreachable (`REGISTRY_UNREACHABLE`). `5` this copy can't be updated in place (`UPDATE_UNSUPPORTED_INSTALL`). The `update` command exists from 1.6.0; update an older CLI once with `npm install -g @miramarket/cli`.

## Account commands

A login is not the same as a trade-ready account — Polymarket orders and live strategy runs also require accepting the platform's Terms/Privacy/Risk Disclosure and having a delegated deposit wallet with the necessary on-chain approvals.

### `miramarket-cli account status [--json]`

Diagnoses trade-readiness across auth, API reachability, region availability, policy acceptance, wallet delegation, and capital. Always exits `0` — `ok:true` means "the check ran," not "everything passed." Read `ready` and `blockers[]`:

```json
{
  "ok": true,
  "command": "account status",
  "ready": false,
  "blockers": [
    {
      "code": "POLICIES_NOT_ACCEPTED",
      "message": "You have not accepted the current Terms, Privacy Policy, and Risk Disclosure.",
      "requiredAction": "A human must run `miramarket-cli account accept-policies` in an interactive terminal.",
      "humanRequired": true
    }
  ],
  "checks": {
    "auth": { "ok": true, "did": "did:privy:...", "expiresAt": "..." },
    "api": { "ok": true },
    "geo": { "ok": true, "country": "GB" },
    "policies": { "ok": false, "accepted": false },
    "wallet": { "ok": true, "delegated": true, "depositWalletAddress": "0x..." },
    "capital": { "ok": true, "cashAtomic": 50000000 }
  }
}
```

If `humanRequired` is `true` on a blocker (not authenticated, wallet not delegated, policies not accepted, region-restricted), surface `requiredAction` and stop — an agent should never attempt to work around these.

Blocker codes: `NOT_AUTHENTICATED`, `API_UNREACHABLE`, `REGION_RESTRICTED`, `POLICIES_NOT_ACCEPTED`, `WALLET_NOT_DELEGATED`, `WALLET_CHECK_FAILED`.

### `miramarket-cli account setup [--json]`

Idempotent — attaches the wallet-level policy and bootstraps the deposit wallet's on-chain approvals; safe to re-run any time. **Cannot complete onboarding by itself**: wallet delegation only happens in the web app in a browser, and this command never accepts policies on your behalf. It reports exactly what's still needed and points at `account accept-policies` or a browser sign-in. Needs a login allowed to trade (**Trade with real money** or **Place orders and bridge**).

### `miramarket-cli account policies [--json]`

Read-only. Shows the current Terms/Privacy/Risk Disclosure versions, your acceptance status, and canonical URLs.

### `miramarket-cli account accept-policies`

Records legal acceptance of the current Terms, Privacy Policy, and Risk Disclosure. This is a human-only action — it requires typing `I accept` in an interactive terminal (or, for a human scripting their own machine, pinning the exact current document versions with `--i-have-read-and-accept --terms-version=... --privacy-version=... --risk-version=...`). An AI agent should never call this on a user's behalf. When any of the three documents changes, the earlier acceptance no longer counts: `account status` reports `POLICIES_NOT_ACCEPTED` until you accept the new versions.

### `miramarket-cli account capital [--json]`

Shows capital currently locked by active strategy runs and pending withdrawal holds — the gap between gross wallet balance and what's actually spendable.

### `miramarket-cli account withdraw --recipient <address> [--amount <usd>] --confirm [--json]`

**Needs the Withdraw funds switch**, which is off by default: approve a login with it on (`login --force`). Without it, exits `3` with a message naming the switch.

Withdraws spendable USDC to an external address. Spendable cash is your USDC on Polygon and Base plus your free perps balance on Hyperliquid; the withdrawal moves the Hyperliquid part out when it needs it, and a small transfer fee comes out of the amount. Margin backing open perp positions does not count until they are closed. Omit `--amount` to withdraw all spendable cash. Requesting more than spendable cash is rejected before anything is moved.

```bash
miramarket-cli account withdraw --recipient 0xabc... --amount 25 --confirm --json
```

Exit codes: `0` ok, `3` auth error, `4` server error (a failed transfer releases its hold automatically), `5` bad input.

## Strategy authoring commands

See [/agent-strategy-guide.md](/agent-strategy-guide.md) for the JSON format itself and the rules for building a strategy that behaves correctly, not just one that passes `validate`.

### `miramarket-cli schema [--format=ts|json|markdown]`

Prints the strategy schema — `ts` for TypeScript types, `json` for a JSON Schema document, `markdown` for a prose authoring guide with worked examples.

### `miramarket-cli strategies generate [prompt] [flags]`

Text-to-strategy. Describe what the strategy should do in plain English and get authoring JSON back, built by the same assistant that powers the visual builder. Requires authentication. Nothing is validated or posted on your behalf: run `validate`, `preview`, and `post` on the result exactly as you would for a hand-written file.

| Flag | Description |
| --- | --- |
| `--out <file>` | Write the strategy JSON here. Without it the strategy is embedded in the result as `strategy`. |
| `--strategy <file>` | Edit an existing local strategy file instead of building from scratch: the prompt is applied as a change to it, and `changeSummary` lists what changed. |
| `--choose <marketId\|n>` | Answer the market question from the previous call (see below): a candidate's market id, or its number as printed. Do not pass a prompt with it. |
| `--selection <id>` | With `--choose`: the `selectionId` the question came with, so a question asked by another session in the meantime is refused rather than answered. |

`result` is one of four values. `ok` is `true` for all of them, because each is a real outcome rather than a failure:

- `strategy` — built. `strategyPath` or `strategy`, plus `markets[]` (what it trades, with the price the generator saw), `stats`, `notices[]`, `unmatched[]`, `changeSummary[]` (edits only), `thesis`, and `nextCommands[]`. A non-empty `unmatched` means something the prompt named was substituted or left out; read it before posting. A [tokenized stock](#tokenized-stock-commands) comes back as a `BASE_STOCKS` leg and a [perp](#hyperliquid-perp-commands) as a `HYPERLIQUID` leg, both with `PRICE_USD` conditions in dollars, ready to post. By default a trade named on one venue also gets one related position on another venue for 30% of the budget, named in `notices` (as in the example below); a prompt with "just", "only", or "nothing else" keeps one venue, and a notice says when the strategy stays on one venue and why.

  `thesis` is set when the prompt asked what to trade about a situation, event, or asset instead of choosing the position ("build a strategy around this week's Fed meeting"). The command researched the news and the markets it moves first, and `thesis` says what the strategy bets on (`bet`), whether it bets with or against the situation (`stance`: `WITH_SITUATION`, `CONTRARIAN`, or `MIXED`), why each market is in it (`legs[]`), what the strategy does (`rules[]`), what would break it (`breaks_if`), the headlines it rests on (`news[]`), and a two-sentence `summary`. Without `--json` the summary prints as a short note. `thesis` is `null` for every other prompt.
- `market_selection` — the request was ambiguous between several markets. `candidates[]` is numbered (`choice`) and the question is saved locally under `selectionId`. When `resumable` is `true`, answer with `strategies generate --choose <marketId|choice> --selection <selectionId>` on the next call; at an interactive terminal the choice is prompted for in place instead. When `resumable` is `false` the question cannot be answered with a choice (the request was an edit, or it named several markets) and `reason` says so; re-run with a prompt that names the market precisely. Any new prompt discards the saved question. A candidate can also be one reading of a vague request rather than a market: it has `outcome` and `venue` set to `OPTION` and its `title` is the reading. Choose it the same way.
- `clarification` — nothing was built; `question` says what is missing. Re-run with a prompt that answers it.
- `answer` — the prompt was a question rather than a build request; `answer` is the reply.

```bash
miramarket-cli strategies generate "buy YES on the Fed cutting rates in December if it drops below 40c, sell at 70c" --out ./fed.json --json
miramarket-cli strategies generate "buy TSLA if it crosses \$400, sell at \$450" --out ./tsla.json --json
miramarket-cli strategies generate "just buy TSLA if it crosses \$400, nothing else" --out ./tsla-only.json --json
miramarket-cli strategies generate "go 3x short on ETH, close it above \$4,200" --out ./eth.json --json
miramarket-cli strategies generate "also sell everything if it drops below 30c" --strategy ./fed.json --out ./fed.json --json
miramarket-cli strategies generate --choose 3215006 --selection a1b2c3d4 --out ./fed.json --json
```

```json
{
  "ok": true,
  "command": "strategies generate",
  "prompt": "buy TSLA if it crosses $400, sell at $450",
  "result": "strategy",
  "strategyPath": "./tsla.json",
  "edited": false,
  "markets": [
    { "market_id": "0xb2000000000000000000001e800a7f5189430cD0", "title": "Tesla Inc. (TSLAc)", "venue": "BASE_STOCKS", "outcome": "LONG", "current_price": 355.69 },
    { "market_id": "561203", "title": "Will Tesla close above $400 on December 31?", "venue": "POLYMARKET", "outcome": "YES", "current_price": 0.38 }
  ],
  "stats": { "actionCount": 3, "conditionCount": 2, "riskProfile": "BALANCED", "heuristicScore": 90 },
  "notices": [
    "Added a related Polymarket market (Will Tesla close above $400 on December 31?) for 30% of the budget ($3 of $10) so the strategy isn't on one venue; ask to remove it for just the TSLA buy."
  ],
  "unmatched": [],
  "changeSummary": [],
  "thesis": null,
  "nextCommands": [
    "miramarket-cli validate ./tsla.json --json",
    "miramarket-cli preview ./tsla.json --json",
    "miramarket-cli post ./tsla.json --demo --json"
  ]
}
```

Exit codes: `0` for every `result`, `3` auth error, `4` generation failed, `5` bad input (`code` says which).

### `miramarket-cli validate <file> [--json]`

Validates a strategy JSON file's structure. Exit `0` valid, `2` validation errors, `5` bad input (missing file, malformed JSON).

```json
{
  "ok": true,
  "command": "validate",
  "strategyPath": "./my-strategy.json",
  "valid": true,
  "errors": [],
  "warnings": []
}
```

### `miramarket-cli preview <file> [--json]`

Summarizes a strategy without contacting the server — node/edge counts, required principal, and `warnings[]` for anything that will be silently dropped or misbehave at import.

### `miramarket-cli edit <file> [flags]`

Updates fields in a local strategy JSON file. Edits apply in memory and the result is fully re-validated before writing — if validation fails, the source file is left untouched and the output reports the errors. `edit` never contacts the server; to change a strategy you have already posted, use [`strategies pull` and `strategies update`](#editing-a-running-strategy).

| Flag | Description |
| --- | --- |
| `--set <path>=<value>` | Set a field (repeatable). Value is parsed as JSON, falling back to string. |
| `--unset <path>` | Remove a field (repeatable). |
| `--out <path>` | Write to a different output file. |
| `--demo` / `--no-demo` | Write or remove `is_demo: true`. |

```bash
miramarket-cli edit ./strategy.json --set initial_principal_usd=100
miramarket-cli edit ./strategy.json --set "nodes[0].condition.threshold=0.7"
miramarket-cli edit ./strategy.json --unset nodes[1].action.risk_guards
```

### `miramarket-cli post <file> [flags]`

Validates and posts a strategy, then starts a run (unless `--no-start`). A live (non-demo) run is judged against the login's budget: within it, the run starts at once after a Polymarket market-health and balance check; beyond it, nothing starts and the strategy waits for the account owner's approval on Connected agents (below). Demo posts need only **Create strategies** and skip the health check.

| Flag | Description |
| --- | --- |
| `--no-start` | Import only, don't start a run. |
| `--name <name>` | Override the strategy name (defaults to its `strategy_id`). |
| `--demo` | Post as a simulation — no real orders placed. |
| `--skip-health-check` | Demo runs only; rejected outright on a live strategy. |
| `--idempotency-key <key>` | Makes retries safe: re-running a post with the same key returns the strategy and run the first attempt created instead of posting again. 1–200 letters, digits, `.`, `_`, `:` or `-`, per account. A key used for a different strategy exits `5` with `IDEMPOTENCY_KEY_REUSED`. |

```json
{
  "ok": true,
  "command": "post",
  "posted": true,
  "started": true,
  "strategyId": "k97abc123...",
  "runId": "k97xyz456...",
  "name": "eth-momentum-v1",
  "demo": false
}
```

A live start beyond the login's budget posts the strategy but starts nothing (`started: false`, `runId: null`) and returns the approval to wait on:

```json
{
  "ok": true,
  "command": "post",
  "posted": true,
  "started": false,
  "strategyId": "k97abc123...",
  "runId": null,
  "approval": { "approvalId": "k57...", "status": "needs_approval", "principalUsd": 500, "budgetUsd": 100, "openLiveUsd": 40, "approveAt": "https://app.miramarket.org/settings/agents" },
  "requiredAction": "This live run is beyond what this login may start on its own. Ask the account owner to approve it on Connected agents (approveAt); it expires in a day.",
  "nextCommand": "miramarket-cli strategies approval k57... --json"
}
```

Once the owner approves, the run starts on its own. `strategies approval` reports it, and re-running the same post with the same `--idempotency-key` returns it too. After the owner denied the request, or it expired or failed, a retry reports that in `approval.status` and `requiredAction`; post again with a new key to ask again.

Exit codes: `0` ok (including a start waiting for approval), `2` validation error, `3` auth error, `4` server error, `5` bad input (including `IDEMPOTENCY_KEY_REUSED`).

### `miramarket-cli strategies approval <approvalId> [--json]`

Where a live start that went beyond the login's budget stands: `pending` (waiting for the owner, with `approveAt`), `started` (with its `runId`), `denied`, `expired` (approvals last a day), or `failed` (with `error`). Exits `5` with `APPROVAL_NOT_FOUND` for an approval that isn't this login's.

## Market data commands

None of these require authentication.

| Command | What it does |
| --- | --- |
| `markets list [--limit <n>] [--offset <n>]` | Lists Polymarket events by id, title, volume. |
| `markets search <query> [--limit <n>]` | Searches events by keyword, sorted by relevance. |
| `markets show <eventId>` | Full event detail: description, end date, volume, liquidity, and each sub-market's outcome prices and CLOB token IDs. |
| `markets orderbook <tokenId> [--depth <n>]` | Live top bids/asks for a CLOB token. |
| `markets prices-history <market> [--interval <interval>]` | Price history; `--interval` is one of `1h`, `6h`, `1d`, `1w`, `1m`, `max`. |

```json
{
  "ok": true,
  "command": "markets show",
  "id": "abc123",
  "title": "Will X happen?",
  "markets": [
    { "id": "...", "question": "...", "outcomePrices": ["0.62", "0.38"], "clobTokenIds": ["...", "..."] }
  ]
}
```

## Tokenized stock commands

Tokenized stocks on Base (AAPLc, TSLAc, NVDAc, PLTRc, MUc, and others) are real equities wrapped as tokens. They are not prediction markets: a strategy buys and sells them as token swaps, and a condition watches them by **share price in dollars**. `markets search` never finds them, so these commands exist instead. None require authentication.

| Command | What it does |
| --- | --- |
| `stocks list` | Every tradable stock with its live pool price. `priced` says how many rows have a usable price; an unpriced row is still listed, just not sizable right now. |
| `stocks show <stock>` | One stock, with the exact `actionTarget` block to paste into an ACTION node. Accepts a ticker (`TSLA`), token symbol (`TSLAc`), company name (`Tesla`), or contract address. |
| `stocks history <stock> [--range 1D\|1W\|1M\|ALL]` | Pool price history, oldest bar first. `1D` is 15-minute bars, `1W` (default) hourly, `1M` 4-hourly, `ALL` daily. |

```json
{
  "ok": true,
  "command": "stocks show",
  "symbol": "TSLAc",
  "ticker": "TSLA",
  "name": "Tesla Inc.",
  "address": "0xb2000000000000000000001e800a7f5189430cD0",
  "priceUsd": 356.47,
  "oraclePriceUsd": 353.33,
  "poolPremiumBps": 89,
  "actionTarget": {
    "venue": "BASE_STOCKS",
    "market": { "market_id": "0xb2000000000000000000001e800a7f5189430cD0", "outcome_token": "LONG", "token_id": "0xb2000000000000000000001e800a7f5189430cD0" }
  },
  "conditionSupported": true,
  "conditionSignal": "PRICE_USD",
  "conditionPriceSource": "chainlink"
}
```

Two prices appear, and they mean different things. `priceUsd` is the pool price, what a swap actually pays, and what a position is sized from. `oraclePriceUsd` is the reference price of the underlying share, what a `PRICE_USD` condition watches; the gap between them is `poolPremiumBps`. `conditionPriceSource` says what a condition watches: `chainlink` for the reference price, or `aerodrome_pool_twap` for a stock with no reference feed yet (MUc, PLTRc), whose `oraclePriceUsd` is `null` and whose conditions watch the pool's 15-minute average price instead. Both are dollars per share, never a 0–1 probability. A large `oracleAgeSeconds` outside US market hours is expected, not a fault.

```json
{
  "ok": true,
  "command": "stocks history",
  "ticker": "TSLA",
  "range": "1W",
  "priceSource": "aerodrome_pool",
  "unit": "USD per token",
  "stale": false,
  "count": 168,
  "firstPriceUsd": 351.12,
  "lastPriceUsd": 356.47,
  "changePct": 1.52,
  "points": [{ "t": 1790000000, "p": 351.12 }, { "t": 1790003600, "p": 351.9 }]
```

`stocks history` charts the pool price (`priceSource` names it), not the reference price. `stale: true` means fresh history was unavailable and the last good reading was returned.

`stocks show` and `stocks history` exit `5` for a company that is not in the registry, and, distinctly, for one that is listed but has no pool to trade in yet (COINc, CRCLc, INTCc). `portfolio` reports stock holdings separately from cash (`stockPositions`, `stockValueUsd`), because a share has to be sold before a strategy can spend the proceeds. Tokenized stocks are geo-restricted: where they are not offered, posting a live strategy that buys one is refused with "Tokenized stocks are not available in your region". `account status --json` shows the region check under `checks.geo`.

## Hyperliquid perp commands

Perps are perpetual futures on Hyperliquid, margined in USDC. They are not prediction markets: a perp has two sides, `LONG` and `SHORT`, never resolves, and is priced in **dollars**. A strategy action on a perp may carry an integer `leverage` (default `1x`), and a condition watches a perp by its **mark price in dollars** (`signal: "PRICE_USD"`). Every price these commands print is dollars, never a 0–1 probability.

There are two kinds of perp:

- Perps on Hyperliquid's main dex: crypto such as `BTC`, `ETH`, and `SOL`. Positions are cross margin: your whole main-dex balance and your other cross positions back them together, so a position's liquidation price depends on all of them, not on its leverage alone.
- HIP-3 perps, listed on Hyperliquid by other providers (the `xyz`, `para`, `io`, and `mkts` dexes): stocks, indices, commodities, FX, rates, and pre-IPO names. Their coin carries the dex (`xyz:NVDA`, `para:10Y`) and their positions are always **isolated** margin: only that position's margin backs it.

Ids are `hl:<COIN>` (`hl:BTC`) or `hl:<dex>:<COIN>` (`hl:xyz:NVDA`), spelled exactly as `perps list` prints them. Coins are case-sensitive (`hl:kPEPE`); never upper-case them.

| Command | Auth | What it does |
| --- | --- | --- |
| `perps list [--dex <name>] [--category <class>]` | No | Every perp with its dex, asset class, margin mode, mark price, 24-hour move, hourly funding, leverage cap, and open interest. |
| `perps show <coin> [--side LONG\|SHORT] [--leverage <n>]` | No | One perp, with the exact `actionTarget` block to paste into an ACTION node. |
| `perps history <coin> [--interval <interval>] [--from <time>] [--to <time>]` | No | Mark-price candles, oldest first. |
| `perps positions` | Yes | Your open perp positions on every dex and your free Hyperliquid balance. |

### `perps list`

| Flag | Description |
| --- | --- |
| `--dex` | Only one dex: its name (`xyz`, `para`, `io`, `mkts`), its display name, or `main` for Hyperliquid's own dex. Any case. An unknown dex exits `5` and names the valid ones. |
| `--category` | Only one asset class: `crypto`, `stocks`, `indices`, `commodities`, `fx`, `rates`, `preipo`, or `other`. Any case. Anything else exits `5`. |

`count` is the rows after the filters and `total` the whole catalog. In a row, `dex` is `""` on the main dex. `funding` is the hourly rate as a fraction; positive means longs pay shorts. `markPx: null` means the price could not be read, not that the perp was delisted.

### `perps show <coin>`

Accepts a ticker (`BTC`, any case), a HIP-3 coin (`xyz:NVDA`), or an id (`hl:BTC`, `hl:xyz:NVDA`). A bare ticker that no main-dex perp carries, such as `NVDA`, resolves to a HIP-3 listing (the one with the most 24-hour volume when several dexes list it), and `resolution` says which; name the dex to pick another. Otherwise `resolution` is `null`.

`actionTarget` is the side `--side` picked (default `LONG`), with `leverage` set only when `--leverage` was given. `actionTargets` always carries both sides. `--leverage` must be a whole number from 1 up to the asset's `maxLeverage`; a higher value exits `5`. `markPx` is what a `PRICE_USD` condition watches, and `minNotionalUsd` is the smallest order the exchange accepts, in position size (margin times leverage).

### `perps history <coin>`

`--interval` is one of `1m`, `5m`, `15m`, `30m`, `1h` (default), `4h`, `12h`, `1d`, `1w`. Without `--from`, the window is the 168 bars ending at `--to` (default now). ### `perps positions`

`withdrawableUsd` is your free USDC on Hyperliquid, summed over every dex; `withdrawableByDex` splits it per dex (`""` is the main dex). It is part of your cash: a withdrawal or a strategy leg on another chain moves it out when needed. `accountValueUsd` also counts margin backing open positions. `liquidationPx` is the mark price at which the exchange force-closes a position, before any exit of yours fires.

```json
{
  "ok": true,
  "command": "perps positions",
  "count": 1,
  "withdrawableUsd": 120.5,
  "withdrawableByDex": { "": 120.5 },
  "accountValueUsd": 770.5,
  "withdrawalSupported": true,
  "positions": [
    { "coin": "ETH", "tokenId": "hl:ETH", "dex": "", "side": "SHORT", "size": 0.5, "entryPx": 4000, "markValueUsd": 1950, "unrealizedPnlUsd": 50, "leverage": 3, "leverageType": "cross", "liquidationPx": 5200, "marginUsedUsd": 650 }
  ]
}
```

Exits `3` without a login and `4` when Hyperliquid is unreachable.

Each perp order needs at least `$10` of position size (margin times leverage), checked when the order is placed, not by `validate`. Funding is charged every hour a position is open. Hyperliquid perps are not available in some regions, including the United States: there, posting a live strategy that opens a perp position is refused with "Hyperliquid perps are not available in your region". See [/agent-strategy-guide.md](/agent-strategy-guide.md) for authoring a perp leg.

## Trading and portfolio commands

### `miramarket-cli trade [flags]`

Places a CLOB limit order directly — for manual/tactical orders, not strategy automation (use `post` under [Strategy authoring commands](#strategy-authoring-commands) for that). Requires authentication and `--confirm`.

**Needs the Place orders and bridge switch.** Each buy must cost (price x size, in USDC) no more than the login's budget, or it exits `3` before anything is signed; sells are never capped. A budget raised on Connected agents applies at once.

| Flag | Required | Description |
| --- | --- | --- |
| `--token-id` | yes | CLOB token ID for the outcome you're trading. |
| `--side` | yes | `buy` or `sell`. |
| `--price` | yes | Limit price between 0 and 1 (e.g. `0.55` = 55¢). |
| `--size` | yes | Number of shares (outcome tokens). A buy costs price x size in USDC: `--price 0.55 --size 10` costs `$5.50`. |
| `--order-type` | no | `FOK` (fill-or-kill, default) or `GTC` (rests on the book). |
| `--confirm` | yes | Required safety flag. |

```bash
miramarket-cli trade --token-id 2174263... --side buy --price 0.55 --size 10 --confirm --json
```

Exit codes: `0` ok, `3` auth error, `4` server error, `5` bad input.

| Command | What it does |
| --- | --- |
| `order status [orderId]` | Status of one order, or all open orders if omitted. |
| `order cancel <orderId> --confirm` | Cancels an open GTC order. Needs **Place orders and bridge**. |
| `balance [--chain base\|polygon\|all]` | USDC balance per chain, plus `cash` (gross minus locked/pending). The free Hyperliquid perps balance appears as a `hyperliquid` entry and counts toward the total and `cash`; margin backing open perp positions does not. |
| `portfolio [--venue polymarket\|base-stocks\|all]` | Balances, open orders, settled positions, tokenized stock holdings, capital reservations. Perp positions are listed by `perps positions`, not here. |

## Strategy management commands

| Command | What it does |
| --- | --- |
| `strategies generate [prompt] [--out <file>]` | Build a strategy from a plain-English description — see [Strategy authoring commands](#strategy-authoring-commands). |

| `strategies rename <strategyId> <name>` | Rename (1–120 characters). |

### `strategies watch <strategyId> [flags]`

| Flag | Description |
| --- | --- |
| `--json` | Blocks, emits exactly one final envelope on completion. |
| `--events` | Emits one NDJSON line per status transition, then a final line — like `login --events`, an exception to "one JSON object per command." |
| `--run <runId>` | Watch a specific run instead of the strategy's latest. |
| `--until <statuses>` | Comma-separated terminal statuses to stop at (default `completed,failed,canceled`). |
| `--timeout <seconds>` | Give up after this long (default 86400); exits `4` with `WATCH_TIMEOUT`. |

| `--fail-on-error` | Exit `4` if the run itself ends `failed`/`canceled` (default: the watch succeeding is exit `0` regardless of run outcome). |


### Editing a running strategy

`strategies pull` and `strategies update` round-trip a strategy that is already running. Only the future part of the graph can change: nodes the run has executed or is waiting on are locked, and so are `root_node_id` and `initial_principal_usd`. Drafts and finished strategies cannot be edited in place — post a new strategy instead.

#### `strategies pull <strategyId> [--out <file>] [--json]`

Writes the strategy as authoring JSON (embedded in the envelope, or to `--out`) and reports which nodes you may touch:

| Field | Meaning |
| --- | --- |
| `editable` | `true` only while a run is active. |
| `lockedNodeKeys` | Nodes you must leave exactly as pulled. |
| `hardLockedNodeKeys` | Executed and in-flight actions: no field or edge changes. |
| `waitingConditionKeys` | Conditions the run is waiting on: their own settings and existing branches are fixed, but they may fan out a new sibling action. |
| `editableNodeKeys` | Everything downstream. |

Nodes keep their `node_id` across the round trip, so `nodes[i]` positions from `pull` are stable for `--set`.

#### `strategies update <strategyId> [file] [--set <path>=<value>] [--unset <path>] [--json]`

Uploads either a file (usually one written by `pull --out`) or the posted graph with dot-path edits applied directly, then saves it. Before anything is sent, the CLI checks the locks and validates the result; the server repeats the checks and additionally rejects edges rewired into the executed past.

| Outcome | Exit | `code` |
| --- | --- | --- |
| A locked node, the root, or the principal changed | 5 | `LOCKED_NODE_EDIT` |
| The edit only touches fields the server does not persist (`risk_guards`, `stabilizers`, `market_selector`) | 5 | `UNSUPPORTED_FIELD` |
| The strategy has no active run | 5 | `NO_ACTIVE_RUN` |
| The edited graph fails validation | 2 | `VALIDATION_ERROR` |
| The server refused the graph (for example an edge rewired into the past) | 5 | `RUN_EDIT_REJECTED` |

An `ABSOLUTE_TIME` condition whose trigger time has already passed is accepted only if you leave it, its decision group, and the actions it gates exactly as pulled; change anything it gates and you must also give it a future time.

```bash
# Pull, edit the file, push it back
miramarket-cli strategies pull <strategyId> --out ./strategy.json --json
miramarket-cli strategies update <strategyId> ./strategy.json --json

# Or edit the posted graph directly
miramarket-cli strategies update <strategyId> --set "nodes[4].condition.threshold=0.35" --json
```

## Bridging commands

Move USDC between Base and Polygon, swap Polygon USDC to USDC.e, or move USDC into your perps balance on Hyperliquid, before trading. All require authentication (the wallet address is resolved from your login). `bridge execute` also needs the **Place orders and bridge** switch, and each `--amount` must be within the login's budget; `bridge quote` needs only read access.

| Command | Description |
| --- | --- |
| `bridge quote --amount <usd> --direction <direction>` | Get a 0x quote. Returns `quoteId`, `transactions[]`, `expectedInputAmount`, `expectedOutputAmount`, `isCrossChain`. |
| `bridge execute --amount <usd> --direction <direction> --confirm [--no-wait]` | Execute the transfer. Returns `quoteId`, `txHash` (the origin transaction), `txHashes[]`, `chainId`, and either `bridgeStatus` (cross-chain) or `settled` (same-chain swap). |
| `bridge status <txHash> --chain-id <8453\|137> [--quote-id <id>]` | Poll a transfer between Base and Polygon by its origin transaction hash (no auth required). It cannot confirm delivery into Hyperliquid. `status` is one of `origin_tx_pending`, `origin_tx_succeeded`, `origin_tx_confirmed`, `origin_tx_reverted`, `bridge_pending`, `bridge_filled`, `bridge_failed`, `unknown`. |

`--direction` is one of `base-to-polygon`, `polygon-to-base`, `polygon-usdc-to-usdce`, `polygon-usdce-to-usdc`, `polygon-to-hyperliquid`, `base-to-hyperliquid`. `polygon-usdc-to-usdce` and `polygon-usdce-to-usdc` are same-chain swaps on Polygon, which have no bridge to poll.

The two `*-to-hyperliquid` directions deliver USDC into your perps balance on Hyperliquid. They are one-way: there is no direction back out. Money leaves Hyperliquid automatically when a withdrawal or a leg on another chain needs it.

By default `bridge execute` waits: `ok: true` means a transfer between Base and Polygon filled, or a same-chain swap confirmed on-chain. It exits `4` in three cases, and none of them is a reason to run `bridge execute` again, because the transaction is already on-chain and a retry would move the funds a second time:

- `BRIDGE_FAILED`: the cross-chain bridge failed. The envelope says whether the funds were refunded on the origin chain.
- `BRIDGE_PENDING`: the cross-chain transfer is still in flight after the polling window. For a transfer between Base and Polygon, poll it with `bridge status <txHash> --chain-id <chainId>` using the values in the envelope. For a `*-to-hyperliquid` transfer, follow it as described below instead.
- `SWAP_UNCONFIRMED`: a same-chain swap on Polygon was submitted but not confirmed within the wait window. There is no bridge to poll. Look up the `txHash` from the envelope on a Polygon block explorer, or run `balance --chain polygon` until the USDC and USDC.e balances reflect the swap.

A `*-to-hyperliquid` transfer is confirmed only by your Hyperliquid balance. `bridge status` cannot see delivery into Hyperliquid, so neither it nor `ok: true` from `bridge execute` proves the USDC arrived. Before you run `bridge execute`, record `withdrawableUsd` from `perps positions --json`. After it returns, whether `ok: true` or `BRIDGE_PENDING`, run `perps positions --json` until `withdrawableUsd` reaches the recorded value plus the amount, less fees; delivery can take up to about ten minutes. A running strategy, a withdrawal, or a perp position opening or closing in the meantime also changes `withdrawableUsd`, so account for those, or move funds while nothing else is using the balance. If it has not arrived after that, check the origin `txHash` on a Base or Polygon block explorer rather than running `bridge execute` again.

```bash
miramarket-cli bridge quote --amount 100 --direction base-to-polygon --json
miramarket-cli bridge execute --amount 100 --direction base-to-polygon --confirm --json
miramarket-cli bridge status 0xabc... --chain-id 8453 --json
miramarket-cli bridge quote --amount 25 --direction polygon-to-hyperliquid --json
```

A strategy funds itself. Posting one that needs USDC on another chain, or on Hyperliquid, moves it on demand, so a manual bridge is only for moving funds ahead of time or for withdrawing.

## Session lifetime

The cached access token lasts 15 minutes, but the CLI also caches a 30-day refresh token (rotated on every use) and silently redeems it at the start of every command — there's no re-login to babysit, on a laptop or an unattended server alike, until the login ends 90 days after it was approved. If the login is revoked (on Connected agents or with `logout`) or has ended, the next command reports `NOT_AUTHENTICATED` and you run `miramarket-cli login` again.
